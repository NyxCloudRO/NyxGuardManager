# Final 5.0.14 candidate layer

This extends the exact accepted Task 7.1 image, preserving all prior source layers and schema 49. `build.sh` verifies that base image identity before building the functional layer, locked security dependency layer, patched Nginx layer, runtime dependency cleanup and verified SQLite replacement. All tags are local; no publishing command is included.

The exporter adds first-match custom WAF 403 observations using the existing bounded Lua queue and retained second vectors. Ordinary upstream 403s, IP/country rules and detector-only events are not counted as custom-rule blocks. Existing operational collector diagnostics and 30-day retention remain authoritative. No request body, URL, cookie, IP or rule identifier becomes a new metric label.

Access Portal Security Rejections are native denied signature or signed-session scope checks persisted once per rejected request in Event Center. A valid candidate session prevents counting other invalid cookies in that same request. Missing cookies, malformed/non-session data, valid-but-expired sessions, incorrect passwords, revoked/password-changed users and administrator-enabled portal bypass are excluded. The latter remains a separate configuration metric. Existing audit retention and deletion policies apply; history before instrumentation is not inferred. Audit-write failure withholds counts and is exposed separately. The shared fallback signing secret is replaced by an installation-specific HMAC key derived from the existing private signing key; explicitly configured secrets remain supported. Former fallback sessions must sign in again.

Both event families are rolling retained-observation gauges for 24h/7d/30d/90d, never lifetime counters. Exact half-open UTC windows, genuine zero and unavailable sources are distinguished. The preferred precise portal family is `nyxguard_access_portal_security_rejections_observed`; no metric claims a confirmed bypass attack. Legacy `_total` gauges remain for existing consumers, with suffix-free gauge aliases. The real audit-write-failure `_total` is a process counter. Native global setting metrics use the same effective defaults as enforcement, including fresh installs.

Use `monitoring/README.md`, the optional mTLS adapter, generator and portable 58-panel dashboard for external monitoring. Node exporter is optional and separately managed. No monitoring service is forced into ordinary installations.

The host updater must accompany this candidate: the prior restore branch referenced undefined variables, and backup manifests lacked engine-transition metadata needed for later restores. Both are corrected in canonical `update.sh`. The installer and Compose retain persistent InnoDB prerequisites and independent VPN Agent 5.0.2 compatibility. Exact clean-install, upgrade, recovery and security evidence is retained privately. Publication remains an owner decision.

Security inputs and exact npm/Python locks are under `security/`. The same OpenResty 1.27.1.2 engine is rebuilt with upstream Nginx's map/regex bounds-check, upstream TLS response and rewrite-escaping fixes, preserving Lua search paths, static modules and GeoIP ABI compatibility. The vendor manifest records raw upstream commits and the adapted four-hunk backport. The version is not artificially increased to evade scanners; version-only findings require the accompanying code-level disposition. Unused AV1 conversion and SSH client helpers are removed; required runtime libraries and certificate/VPN behavior are qualified separately. Do not equate a successful scan execution with a clean security decision: consult the final acceptance report.

The final runtime explicitly retains JSON-string database responses for compatibility with the upgraded MySQL client. Its system SQLite 3.54.1 library is built from the vendor SHA3-verified source into a separately versioned Debian package, with Python ABI/query/integrity checks. Runtime npm is removed after native dependency checks; app deployment does not execute npm. The supported application database remains MariaDB with schema 49.

Automatic-ban metrics require the native `rule_origin=automatic_ban` provenance field. A manual rule with an Auto-ban-like note is excluded. The updater retains its strict storage identity checks while tolerating only unrelated transient containers independently confirmed to have disappeared during inventory.
